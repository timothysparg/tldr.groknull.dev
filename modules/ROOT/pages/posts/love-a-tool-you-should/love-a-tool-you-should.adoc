I've always liked the idea of git hooks, but my first real encounter with them was clunky.
It was a Java project using https://github.com/typicode/husky[Husky], a great tool, but depending on Node.js in a Java codebase felt out of place.
https://github.com/pre-commit/pre-commit[pre-commit] is similar: solid, but most at home in the Python ecosystem.

For a long time https://github.com/evilmartians/lefthook[Lefthook] was my go-to: a single binary, not tied to any ecosystem.
But one thing kept gnawing at me with all of these tools: every developer still has to install and configure them before the hooks do anything.

## The Missing Piece

I've recently become quite fond of the https://github.com/jdx[jdx] ecosystem for developer focused tooling. Whilst each tool is a separate project their superpower is that they are designed to be used together. It's one of those cases where the whole is greater than the sum of its parts.

In this instance it's the combination of https://github.com/jdx/mise[mise] and https://github.com/jdx/hk[hk] that finally stopped it gnawing at me. +
Whilst `hk` itself is focused on being a git hook manager, if we utilise the integration with `mise` we can get git hooks that get installed automatically with all the other tools the project requires.

Your quickstart boils down to the following steps:

====
. `git clone`
. `mise trust`
. `mise install`
====

That's it. `Mise` will read the `mise.toml` file and install all the required tools, including `hk`. It will also install the git hooks automatically.

Let's dig a little deeper and look at an example.

```toml
[tools] <1>
hk = "latest"
actionlint = "latest"
java = "21@temurin"
"github:google/google-java-format" = "latest"

[env]
HK_MISE = true <2>

[hooks]
postinstall = "hk install --global --mise" <3>
```

<1> Every tool the project needs, pinned in one place
<2> Hooks run inside the `mise` environment, with the exact tool versions above
<3> The magic: git hooks installed straight after the tools

[NOTE]
====
`--global` needs https://github.blog/open-source/git/highlights-from-git-2-54/#h-config-based-hooks[Git 2.54+]. On older Git, use `hk install --mise` for a per-repo install
====

A minimal `hk.pkl` would look like this:

```pkl
amends "package://github.com/jdx/hk/releases/download/v2.2.0/hk@2.2.0#/Config.pkl"
import "package://github.com/jdx/hk/releases/download/v2.2.0/hk@2.2.0#/Builtins.pkl"

steps { <1>
  ["actionlint"] = Builtins.actionlint <2>
  ["google_java_format"] { <3>
    glob = List("**/*.java")
    exclude = List("**/target/**")
    check = "google-java-format --dry-run --set-exit-if-changed {{files}}"
    fix = "google-java-format --replace {{files}}"
    batch = true
  }
  ["mise"] = Builtins.mise
}

hooks {
  ["commit-msg"] { <4>
    steps {
      ["check_conventional_commit"] = Builtins.check_conventional_commit
    }
  }
}
```

<1> Top-level steps feed hk's predefined `check`, `fix`, and `pre-commit` hooks
<2> hk ships with over 150 https://hk.jdx.dev/builtins[builtins]
<3> Inline linter declaration
<4> Other hooks are declared explicitly


Each of the builtins is just a definition of its usage pattern in the https://github.com/jdx/hk/blob/main/pkl/builtins/google_java_format.pkl[hk repository].

```pkl
 ["google_java_format"] {
    glob = List("**/*.java")
    exclude = List("**/target/**")
    check = "google-java-format --dry-run --set-exit-if-changed {{files}}"
    fix = "google-java-format --replace {{files}}"
    batch = true
  }
```

[IMPORTANT]
====
hk runs your linters. mise installs them. Skip mise, and that part's on you
====

What I love about combining these two tools is that `mise.toml` becomes the single source of truth.
Need to upgrade a tool, or add a new one? Update `mise.toml`, and everyone else on the project picks up the change the next time they pull.

But let's hook back around to hk, shall we?
With mise looking after the tools, hk can focus on what it does best: managing git hooks, without anyone having to install hk or the hooks themselves.

## Loving it enough to improve it

As much as I love hk, there's still room for improvement, and as a user it's in my interest to help make it better.
So over a couple of days I opened six PRs against hk.
Within a few days, five were merged. One very much wasn't.

### New builtins

I like https://github.com/google/google-java-format[google-java-format], but I wanted to just write `Builtins.google_java_format` instead of the full `google_java_format` definition.
So I added it as a https://hk.jdx.dev/builtins.html#google-java-format[builtin] in https://github.com/jdx/hk/pull/777[#777] pass:[<span class="pr-status merged">Merged</span>].

I often use Docker Compose files in my projects, and I'd recently come across https://github.com/zavoloklom/docker-compose-linter[docker-compose-linter].
I'm no expert on Compose best practices, so I'm happy to lean on a linter to tell me when I'm doing something wrong.
I added it as the https://hk.jdx.dev/builtins.html#dclint[`dclint` builtin] in https://github.com/jdx/hk/pull/779[#779] pass:[<span class="pr-status merged">Merged</span>].

### Better docs for the mise setup

Using mise to bootstrap hk is one of the most underrated features of the ecosystem, but the docs didn't highlight this pattern.
I had a quick discussion with https://jdx.dev/[Jeff Dickey] about the different approaches, and we agreed on a https://github.com/jdx/hk/discussions/754[recommended setup].
I added it to hk's https://hk.jdx.dev/mise_integration.html[mise integration docs] in https://github.com/jdx/hk/pull/780[#780] pass:[<span class="pr-status merged">Merged</span>].

[WARNING]
====
This is already out of date.
hk's docs have since moved on to a one-off `hk install --global --mise` (Git 2.54+), which is what the <<_the_missing_piece,setup above>> uses.
====

### Friendlier configuration

hk's Pkl schema had a couple of papercuts worth fixing.

#### Excludes that are never null

Say you wanted the `newlines` builtin to skip SVG files. You would instinctively try to append to its `exclude` list:

```pkl
  ["newlines"] = (Builtins.newlines) {
    exclude = Builtins.newlines.exclude + List("**/*.svg")
  }
```

However, this required that the builtin config had an `exclude` field, and that it wasn't null.
If you wanted to be safe you ended up doing this:

```pkl
  ["newlines"] = (Builtins.newlines) {
    exclude = (Builtins.newlines.exclude ?? List()) + List("**/*.svg")
  }
```

which gave me the _ick_. 
So in https://github.com/jdx/hk/pull/781[#781] pass:[<span class="pr-status merged">Merged</span>] I gave `exclude` an empty list as its default in `pkl/Config.pkl`.
That means it's never null, you can always append to it, and the first snippet just works.

#### Steps that need configuration

I wanted to add the https://github.com/google/addlicense[addlicense] linter as a builtin to hk, but out of the box it added a Google license header to every file, which wasn't much use unless you worked at Google.
To use your own license you'd have needed to override both the `check` and `fix` commands:

```pkl
  ["addlicense"] = (Builtins.addlicense) {
    check = "addlicense --check -f MY_LICENSE {{files}}"
    fix = "addlicense -f MY_LICENSE {{files}}"
  }
```

at which point the builtin wasn't adding much value.
addlicense can take a `LICENSE_FILE`, so it made sense for that to be required.
I tried a few ways of doing this, and they all felt a bit clunky.
The least hacky was https://hk.jdx.dev/configuration.html#step-step-condition-string[`step_condition`]:

```pkl
step_condition = "exec('if [ -n \"$LICENSE_FILE\" ] && [ -f \"$LICENSE_FILE\" ]; then echo -n 1; fi') == '1'"
```

It worked, but it didn't feel like what `step_condition` was intended for.

So in https://github.com/jdx/hk/pull/785[#785] pass:[<span class="pr-status merged">Merged</span>] I added a https://hk.jdx.dev/configuration.html#step-required-list-string[`required`] field.
A step can now declare the environment variables it needs, and use them in its commands:

```pkl
  ["addlicense"] {
    glob = List("**/*.java")
    required = List("LICENSE_FILE")
    check = "addlicense --check -f $LICENSE_FILE {{files}}"
    fix = "addlicense -f $LICENSE_FILE {{files}}"
  }
```

Until `LICENSE_FILE` is set, whether in your shell, mise's `[env]` or hk's own `env` block, hk skips the step and says why.  
Now that that `required` field is available I should probably submit a PR to add it to the builtins, so that others can use it too.

### The one that didn't land

The https://hk.jdx.dev/cli/util/trailing-whitespace.html[trailing_whitespace] builtin also strips trailing whitespace from Markdown files.
I didn't think that was a good default, because trailing whitespace has semantic meaning in Markdown, so I opened https://github.com/jdx/hk/pull/778[#778] pass:[<span class="pr-status closed">Closed</span>] to exclude `.md` files.

jdx's reply, in full: "I disagree".

It's exactly what I'd want from a maintainer: a clear, unambiguous answer, not weeks of polite back and forth.
Open source projects need strong leadership and someone with a distinct direction, and that was evident here.
